# Key Portal Deployment and Backend Setup

## Current state

The static frontend lives in `key-portal/` and is designed for GitHub Pages. It is intentionally fail-closed: the Generate button stays disabled until public endpoint configuration is provided. No keys are issued by the frontend itself.

- `index.html`: accessible portal UI and API client
- `style.css`: responsive styling
- `portal-config.js`: public configuration placeholders only

## Hosting plan

1. Publish the contents of `key-portal/` to GitHub Pages using the workflow in `.github/workflows/pages.yml`.
2. Use a separate PIXORA-owned Supabase project for the private API and database. Do not use the existing unrelated Supabase project.
3. Use Cloudflare Turnstile for the browser challenge. Its site key is public; its secret belongs only in the backend's secret store.
4. Configure the Pages origin in the backend's CORS allowlist and configure `apiBaseUrl` and `turnstileSiteKey` in `portal-config.js`.
5. Test issuance and activation in a staging environment before enabling production issuance.

The Pages URL will typically be `https://azuremc-projects.github.io/PIXORA/` if GitHub Pages is configured to deploy this repository's workflow artifact; the portal files will be at the site root only if the workflow artifact points at `key-portal/`. Confirm the published URL in repository Settings → Pages after deployment.

## API contract

### POST `/issue-key`

Request JSON:

```json
{ "captchaToken": "token-from-turnstile" }
```

Successful response (display only once):

```json
{ "key": "PIX-....", "expiresAfterSeconds": 864000 }
```

The backend must verify the Turnstile token with Cloudflare using a server-side secret, apply per-IP and global issuance limits, generate a high-entropy key using a cryptographically secure random generator, store only a cryptographic hash, and return the raw key only in the HTTPS response. Add `Cache-Control: no-store` to responses. Never log the raw key or CAPTCHA token.

### POST `/activate-key`

The client submits the key and a public installation-key value generated by the app. The backend must atomically redeem the key only if it has never been redeemed, bind it to that installation public key, and set expiry to server time plus 10 days. Return a signed, short-lived entitlement or session result. The private installation key stays on the device in secure storage where available.

### POST `/check-entitlement`

The app presents its signed entitlement/session and installation public key. The server checks signature/session status, expiry, revocation, and installation binding. Do not trust the local device clock or a client-provided expiry.

## Database and abuse controls

Implement the key database and atomic redemption with migrations and server-side functions. Required controls:

- Key hashes are unique; redeemed keys cannot be reset by clients.
- Use a transaction or a single atomic database function to avoid simultaneous redemption races.
- Enable row-level security on exposed tables and do not grant browser clients direct access to key records.
- Add IP-based issuance limits, a global issuance cap, monitoring, and an emergency kill switch. Be careful not to retain raw IPs longer than necessary; define retention and privacy practices.
- Return generic errors and add CORS allowlisting. CORS is not authentication and must not be the only abuse control.
- Keep service-role/database secrets and Turnstile secret out of the public repository and frontend bundle.

## Important product limitation

No-email, no-account key issuance cannot reliably enforce one key per human. Bot challenges and rate limits reduce automated abuse but do not prove unique identity. A public, open-source client can also be modified locally; the server can enforce rules for the official hosted service and official builds, not every fork.
